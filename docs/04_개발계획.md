# 카페 운영 프로그램 1차 개발계획

확인일: 2026-10-12  
상태: 사용자 확인 완료. 제안된 계획에 사용자가 “ㅇ”으로 확인했다. 계획 확인은 PRD·FRD에 남은 미정 계산·업무 기준의 승인을 뜻하지 않는다.

## 1. 전체 작업 순서와 개수

전체 순서는 **판매 기록과 메뉴 수익성 → 비용·매장 손익과 재료 잔량 → 재고 기록과 백업·복원**이다.

**총 EPIC 3개, User Story 14개**다. EPIC은 함께 완성할 작업 묶음이고, Story는 사용자가 한 가지 목적을 달성하는 기능 단위다.

| 순서 | EPIC | Story 수 | 끝나면 화면에서 확인할 결과 |
| --- | --- | ---: | --- |
| 1 | 판매 기록과 메뉴 수익성 | 4개 | 판매를 입력·수정·삭제하고 메뉴별로 남는 금액 확인 |
| 2 | 비용·매장 손익과 재료 잔량 | 5개 | 비용을 관리하고 판매가 손익·잔량에 연결되는 것 확인 |
| 3 | 재고 기록과 전체 백업·복원 | 5개 | 입고·폐기·실측을 반영하고 백업 시점으로 복원 |

판매가 원가·손익·재료 사용량의 출발점이므로 먼저 만든다. 다음으로 비용과 잔량 조회를 연결하고, 마지막에 재고 변동 입력과 전체 복원을 완성한다. 재고 조회는 기존 자료로 먼저 구현하므로 EPIC 2에서도 실제 잔량을 확인할 수 있다.

공통 화면, 초기 샘플 준비, 기록 저장소, 계산 함수는 각 Story에 필요한 선행 작업으로 포함한다. 화면이나 기술 기반만 만드는 별도 EPIC은 두지 않는다.

근거 문서: `docs/01_PRD.md`, `docs/02_FRD.md`, `docs/03_TRD.md`, `design/warm_cafe_operations/DESIGN.md`, `design/_1`~`design/_4`의 화면 이미지와 HTML.

실제 확인 내용은 `docs/05_테스트결과.md`에 기록한다. EPIC 1의 관련 FRD 기준은 2026-10-12 사용자의 A 선택 및 “모두 추천대로” 답변을 근거로 해당 문서의 결정 기록에 남긴다. 이 진행표의 ‘검사 수행’은 사용자 합격 판정을 뜻하지 않는다.

- 실제 기록으로 계산하고 실제 저장소에 보관한다. 시안의 예시 숫자나 저장되는 척하는 동작으로 완료하지 않는다.
- 변경 기능은 새로고침 후에도 결과가 유지돼야 한다.
- 잘못된 입력·취소·저장 실패에는 기존 기록이 유지돼야 한다.
- 자동 검사와 실제 브라우저 확인을 모두 수행한다.
- 이후 화면이 추가되면 앞서 만든 변경 기능과의 연결도 다시 검사한다.

FRD에 남아 있는 수수료 입력, 새 날짜의 마감 상태, 같은 날 실사 순서, 폐기 손실의 손익 반영, 반올림 등은 **관련 Story의 계산 기준을 확정하기 위한 선행 조건**이다. 계획 확인만으로 이 기준까지 승인된 것으로 취급하지 않는다. 기술 구현은 TRD를 따르고 미정 업무 기준은 임의로 결정하지 않는다.

아래 숫자 예시는 별도 검사 자료를 사용하며 원본 샘플의 실적이라고 표현하지 않는다. 자동 검사는 개발 시 수행할 계획이며 현재 통과했다는 뜻은 아니다.

## 3. EPIC 1. 판매 기록과 메뉴 수익성

**포함:** S01~S04  
**의존성:** 초기 자료·저장소 준비 → 판매 등록 → 수정·삭제 → 수익성 조회

### S01. 판매 기록을 새로 남긴다

- **사용자가 할 수 있는 일:** 판매일·메뉴·채널·수량·단가·할인·수수료를 기록한다. 입력 항목은 FRD 기준 확정 후 적용한다.
- **자동 검사:** 초기 샘플이 한 번만 준비되는지, 순매출·원가·수수료 계산, 채널별 포장재 적용, 필수값 누락과 중복 저장 방지, 저장 실패 시 기존 자료 보존을 검사한다.
- **화면 확인 행동과 예상 결과:** 판매 한 건을 저장하고 새로고침한다. 목록에 한 번만 나타나고 입력값이 유지돼야 한다. 잘못된 수량을 입력하면 이유가 표시되고 저장되지 않아야 한다.

### S02. 잘못된 판매 기록을 수정한다

- **사용자가 할 수 있는 일:** 기존 판매를 열어 잘못된 값을 바로잡는다.
- **자동 검사:** 수량·할인 변경에 따른 재계산, 당시 원가 보존, 날짜 변경 시 이전·새 기간 반영, 변경된 기준이 필요한 경우의 처리를 검사한다.
- **화면 확인 행동과 예상 결과:** 수량을 수정해 저장한다. 새 행이 추가되지 않고 기존 행의 금액이 바뀌어야 한다. 취소하면 기존 값이 유지되고, 새로고침해도 저장된 수정값이 남아야 한다.

### S03. 잘못 등록한 판매 기록을 삭제한다

- **사용자가 할 수 있는 일:** 삭제 대상을 확인하고 판매 기록을 제거한다.
- **자동 검사:** 대상 기록만 삭제되는지, 취소 시 유지되는지, 반복 요청으로 다른 기록이 삭제되지 않는지, 관련 계산에서 제외되는지 검사한다.
- **화면 확인 행동과 예상 결과:** 삭제를 취소하면 행이 유지된다. 삭제를 확정하면 행이 사라지고 새로고침해도 다시 나타나지 않아야 한다.

### S04. 메뉴별로 얼마나 남는지 확인한다

- **사용자가 할 수 있는 일:** 일·월을 선택해 메뉴별 매출·직접 비용·남는 금액을 확인한다.
- **자동 검사:** 판매별 계산과 메뉴 합계의 일치, 합계 기준 수익률, 여러 당시 가격의 처리, 순매출 0과 원가·수수료 누락 처리를 검사한다.
- **화면 확인 행동과 예상 결과:** FRD 검사 예시에서는 순매출 47,000원에서 원가 12,000원과 수수료 700원을 반영해 **34,300원**이 남아야 한다. 판매를 수정·삭제하면 같은 기간의 메뉴 결과도 바뀌어야 한다.

**EPIC 완료 기준:** 판매 등록·수정·삭제와 일·월 메뉴 수익성이 실제 저장 기록으로 연결된다. 시안 `_3`과 `_4`에 해당하는 화면에서 결과를 확인하고 재접속 후에도 기록이 유지된다.

## 4. EPIC 2. 비용·매장 손익과 재료 잔량

**포함:** S05~S09  
**의존성:** EPIC 1 완료 → 비용 관리 → 손익 조회. 재료 잔량은 초기재고·기존 재고기록·판매 사용량에 의존한다.

### S05. 비용을 새로 남긴다

- **사용자가 할 수 있는 일:** 비용이 해당하는 날짜·항목·금액을 기록한다.
- **자동 검사:** 귀속 기간 처리, 필수값·금액 검사, 기존 배분 비용과 신규 입력의 구분, 반복 저장 방지를 검사한다.
- **화면 확인 행동과 예상 결과:** 비용을 저장하면 해당 날짜·항목·금액이 목록에 나타난다. 새로고침해도 남아 있고, 잘못된 금액은 저장되지 않아야 한다.

### S06. 잘못된 비용 기록을 수정한다

- **사용자가 할 수 있는 일:** 기존 비용의 날짜·항목·금액을 바로잡는다.
- **자동 검사:** 기존 행 수정, 금액 변경, 귀속일 변경 시 이전·새 기간 반영, 취소·저장 실패 처리를 검사한다.
- **화면 확인 행동과 예상 결과:** 비용 금액을 수정하면 기존 행만 바뀐다. 날짜를 바꾸면 이전 날짜 목록에서 빠지고 새 날짜에 나타나야 한다.

### S07. 잘못 등록한 비용 기록을 삭제한다

- **사용자가 할 수 있는 일:** 불필요하거나 중복 입력한 비용을 제거한다.
- **자동 검사:** 대상 비용만 삭제되는지, 취소 시 유지되는지, 기간 비용 합계에서 빠지는지 검사한다.
- **화면 확인 행동과 예상 결과:** 삭제 취소 시 그대로 남고, 확정 시 목록에서 사라진다. 새로고침 후에도 삭제 상태가 유지돼야 한다.

### S08. 기간별 매장 손익을 확인한다

- **사용자가 할 수 있는 일:** 일·월을 선택해 매출·원가·수수료·기간 비용과 손익을 확인한다.
- **자동 검사:** 메뉴 결과와 손익의 연결, 비용 중복 집계 방지, 월계획을 다시 더하지 않는지, 미마감·일부 기간·누락 자료 처리를 검사한다.
- **화면 확인 행동과 예상 결과:** FRD 검사 예시에서 남는 금액 34,300원에 기간 비용 5,000원을 반영하면 기본 손익은 **29,300원**이다. 비용 수정·삭제에 따라 결과가 바뀌어야 한다. 미마감 날짜를 매출 0이나 월말 예상으로 채우면 안 된다.

### S09. 재료 잔량과 소진 상태를 확인한다

- **사용자가 할 수 있는 일:** 기준일의 재료별 잔량·최근 실측 기준·소진·음수 상태를 확인하고 재료를 찾아본다.
- **자동 검사:** 초기재고·기존 입고·폐기·실사·판매 사용량의 연결, 채널별 사용량, 판매 수정·삭제와 실사 전후 처리, 서로 다른 단위의 합산 방지를 검사한다.
- **화면 확인 행동과 예상 결과:** 판매 수량을 바꾸면 관련 재료의 잔량이 정해진 기준에 따라 바뀐다. 잔량 0은 소진, 음수는 기록 점검 필요, 근거 누락은 확인 불가로 구분돼야 한다.

**EPIC 완료 기준:** 판매 입력 → 메뉴 수익성 → 매장 손익 → 재료 잔량의 핵심 흐름이 실제 화면에서 연결된다. 비용 입력·수정·삭제가 손익에 반영되고, 기존 재고자료를 이용한 잔량 계산이 검증된다.

## 5. EPIC 3. 재고 기록과 전체 백업·복원

**포함:** S10~S14  
**의존성:** EPIC 2의 잔량 계산 → 재고 변동 입력. 전체 백업·복원은 모든 기록과 기준 자료의 저장 구조에 의존한다.

### S10. 재료 입고를 기록한다

- **사용자가 할 수 있는 일:** 날짜·재료·입고 수량과 필요한 정보를 기록한다.
- **자동 검사:** 입고 증가량, 기준단위 검사, 잘못된 수량·재료, 반복 저장·저장 실패 처리를 검사한다.
- **화면 확인 행동과 예상 결과:** 우유 1,000ml를 입고하면 해당 기준 이후 잔량에 1,000ml가 한 번만 반영된다. 취소하면 변하지 않고 새로고침해도 저장 결과가 유지돼야 한다.

### S11. 재료 폐기를 기록한다

- **사용자가 할 수 있는 일:** 폐기한 재료와 양을 기록한다.
- **자동 검사:** 폐기 감소 처리, 원본 음수 기록과 입력 수량의 부호 처리, 잘못된 값과 음수 잔량 발생 시 확정된 대응을 검사한다.
- **화면 확인 행동과 예상 결과:** 우유 200ml를 폐기하면 잔량이 200ml 감소해야 한다. 폐기를 두 번 빼거나 재고를 증가시키면 안 된다. 손익 반영은 별도로 확정된 FRD 기준을 따른다.

### S12. 실제로 센 재고를 기록한다

- **사용자가 할 수 있는 일:** 실제 센 수량을 기록하고 장부와의 차이를 확인한다.
- **자동 검사:** 실측량을 기준으로 삼는지, 차이량 중복 반영 방지, 실측 0 처리, 실사 전 판매 수정과 이후 변동 처리를 검사한다.
- **화면 확인 행동과 예상 결과:** 우유 실측 2,000ml를 기록한 뒤 이후 입고 1,000ml와 판매 사용 400ml가 있으면 잔량은 **2,600ml**여야 한다. 실측 당시 차이를 다시 차감하면 안 된다.

### S13. 전체 기록을 백업 파일로 보관한다

- **사용자가 할 수 있는 일:** 저장된 전체 기록과 기준 자료를 JSON 파일로 내려받는다.
- **자동 검사:** 모든 기록 묶음 포함, 한 저장시점의 일관성, 당시 원가·단위·빈칸 보존, 미저장 입력 제외, 파일 생성 실패 처리를 검사한다.
- **화면 확인 행동과 예상 결과:** 백업을 누르면 시점을 구분할 수 있는 파일이 내려받아진다. 화면 입력 중인 미저장 값은 포함되지 않으며, 실패를 백업 완료로 표시하면 안 된다.

### S14. 백업 시점의 전체 기록으로 복원한다

- **사용자가 할 수 있는 일:** 백업 파일을 선택하고 전체 교체 영향을 확인한 뒤 복원한다.
- **자동 검사:** 정상 복원 후 기록·결과 일치, 손상·지원 불가 버전·중복 번호·기준 자료 누락 거절, 취소·중간 실패 시 기존 자료 유지, 부분 복원 방지를 검사한다.
- **화면 확인 행동과 예상 결과:** 백업 후 판매·비용·재고를 변경한 다음 복원한다. 모든 기록과 핵심 결과가 백업 시점으로 돌아가야 한다. 잘못된 파일이나 복원 취소에는 현재 기록이 그대로 남아야 한다.

**EPIC 완료 기준:** 입고·폐기·실측 기록이 실제 잔량에 반영되고, 전체 백업·복원이 화면과 파일에서 검증된다. 네 화면의 연결, 재접속, 저장 실패 대응을 최종 확인한다.

## 6. 개발 시간과 최종 확인

PRD의 **기획 25분·화면 설계 20분·개발 115분·검사 50분·배포 30분**, 총 4시간 목표를 유지한다. 자동 검사와 기본 오류 대응은 각 Story 작업에 포함하고, 검사 50분에는 실제 브라우저에서의 연결·복원 검사를 집중한다.

각 EPIC의 결과는 로컬 또는 Vercel 미리보기에서 확인한다. 마지막에는 GitHub에 코드가 보관되고 Vercel 운영 주소에서 핵심 흐름이 작동하는지 확인한다. 배포는 별도 사용자 기능 Story로 세지 않지만 완료 조건에서 빠뜨리지 않는다.

4시간은 계정·권한과 필요한 업무 기준이 준비된 경우의 목표다. 시간이 부족하다고 저장·계산·검사를 생략하거나 가짜 동작으로 완료 처리하지 않는다.
